# hookify vs. Lelu — expansion-aware policy comparison

Generated by `benchmarks/run.sh` — not hand-edited.
Regenerate after any change to the corpus below or to policy/hookify logic.

hookify side: its own documented example rule (`pattern: rm\s+-rf`, from
`commands/hookify.md` in anthropics/claude-code), evaluated by this plugin's
own hookify-fidelity-tested matcher — not a re-implementation for this benchmark.
Lelu side: the real Tier-1 policy (`policies/defaults.json`) via `AnalyzeCommand`
+ `PolicySet.Evaluate` — the same code path every real tool call goes through.

## Destructive cases (should be caught)

| Command | Note | hookify | Lelu |
|---|---|---|---|
| `rm -rf ~/` | the viral case verbatim | matched | deny |
| `rm -rf $HOME` | env-var form of the same target | matched | deny |
| `rm -rf ${HOME}/` | braced env-var form | matched | deny |
| `sudo rm -rf ~/` | sudo-prefixed | matched | deny |
| `cd /tmp && rm -rf ~/` | chained after an unrelated command | matched | deny |
| `rm -fr ~/` | flags reversed, same meaning | — | deny |
| `rm -r -f ~/` | flags as separate arguments | — | deny |
| `rm --recursive --force ~/` | long-form flags | — | deny |
| `rm -rf "$HOME"` | quoted env-var form | matched | deny |
| `rm -rf .` | relative path resolving to home via cwd | matched | deny |

## Benign cases (should NOT be caught — false-positive check)

| Command | Note | hookify | Lelu |
|---|---|---|---|
| `rm -rf node_modules` | routine cleanup, not a protected path | matched | allow |
| `rm -rf ./dist` | routine cleanup, not a protected path | matched | allow |
| `grep -r "rm -rf" .` | searching source for the pattern, not running it | matched | allow |
| `echo "never run rm -rf on prod"` | the text appears inside a string literal, not a command | matched | allow |

## Summary

- Destructive cases caught — hookify: 7/10, Lelu: 10/10
- False positives on benign cases — hookify: 4/4, Lelu: 0/4

hookify catches most of the destructive cases too — its regex matches the literal
text "rm -rf" wherever it appears, which is exactly the problem: it can't tell a
destructive target from a safe one, or a command from a string that merely mentions
one. The gap that matters isn't catch rate on the obvious cases — it's precision:
false positives on routine developer commands, and the specific literal-text misses
above (reversed/separated/long-form flags) that a fixed regex has to enumerate by
hand and expansion-aware parsing gets for free.
